# OpenResponses as the canonical IR: source notes

Checked 2026-09-24 against the official [specification](https://www.openresponses.org/specification), [reference](https://www.openresponses.org/reference), [dated OpenAPI 3.1 schema](https://www.openresponses.org/openapi/2026-04-24/openapi.json), [changelog](https://www.openresponses.org/changelog), and [source repository](https://github.com/openresponses/openresponses). This note distinguishes the standard's requirements from recommendations for this router.

## Pin and scope

- The current published release is `2026-04-24` (`info.version` in the [dated OpenAPI document](https://www.openresponses.org/openapi/2026-04-24/openapi.json)); the [changelog](https://www.openresponses.org/changelog#2026-04-24) lists WebSocket, compaction, assistant message `phase`, and optional output-text logprobs as changes since `2026-01-15`. The [upstream README](https://github.com/openresponses/openresponses#whats-in-this-repo) calls `/openapi/openapi.json` the latest schema and `/openapi/<YYYY-MM-DD>/openapi.json` dated releases. Generate or audit against the dated release, not a floating URL. The two URLs had semantically identical JSON on the check date (only two JSON property orders differed).
- This is a common multi-provider API contract, **not** a promise of lossless cross-provider conversion: the [extension rules](https://www.openresponses.org/specification#extending-items) say extended item types and trajectories containing them are implementation-specific. The [2026-04-24 schema](https://www.openresponses.org/openapi/2026-04-24/openapi.json) has only function tools in `ResponsesToolParam`; it does not define every OpenAI-hosted tool or every model modality as a standard input type.
- The official repo contains [site-local Kubb/Zod output](https://github.com/openresponses/openresponses/tree/main/src/generated/kubb) produced with its [generation script](https://github.com/openresponses/openresponses/blob/main/package.json), but the canonical published contract is the dated OpenAPI schema. The site's generated code is not a public normative TypeScript package.

## Canonical data model

- [CreateResponseBody](https://www.openresponses.org/openapi/2026-04-24/openapi.json): `model`, `input` (plain string or ordered `ItemParam[]`), `previous_response_id`, `instructions`, `tools`, `tool_choice`, `text`, `reasoning`, `max_output_tokens`, `parallel_tool_calls`, `stream`, `background`, `store`, `truncation`, `include`, and the sampling/metadata options belong to the request schema. Do not reduce the canonical request to `messages: {role, content: string}[]`. A string `input` is interpreted as a user message; tool outputs enter subsequent requests as items identified by `call_id` ([reference, request body](https://www.openresponses.org/reference#request-body), [spec, previous_response_id](https://www.openresponses.org/specification#previous_response_id)).
- Input [ItemParam](https://www.openresponses.org/openapi/2026-04-24/openapi.json) is a discriminated union of item reference, reasoning, compaction summary, user/system/developer/assistant messages, function call, and function call output. User message content is a string or ordered `input_text | input_image | input_file` parts; assistant message input supports `output_text | refusal`; `FunctionCallOutputItemParam.output` is a string or array of text/image/file/video parts. Output [ItemField](https://www.openresponses.org/openapi/2026-04-24/openapi.json) includes `Message`, `FunctionCall`, `FunctionCallOutput`, `ReasoningBody`, and `CompactionBody`. There is no standard `input_audio` item in this dated schema. Output message `phase` (`commentary | final_answer`) should be preserved in assistant messages sent on follow-up ([schema, `Message` and `AssistantMessageItemParam`](https://www.openresponses.org/openapi/2026-04-24/openapi.json)).
- Output [ResponseResource](https://www.openresponses.org/openapi/2026-04-24/openapi.json) is a complete response snapshot: `id`, `object`, timestamps, `status`, `incomplete_details`, `model`, ordered `output`, `error`, `usage`, and echoed options including tools. All 31 named top-level properties are in its `required` list; many are nullable (`usage`, `completed_at`, `error`, etc.). `Usage` requires input/output/total tokens and cached/reasoning-token detail when present. A router should not fabricate unavailable upstream usage; `usage: null` is legal.
- Standard tools are [FunctionToolParam](https://www.openresponses.org/openapi/2026-04-24/openapi.json) objects. `tool_choice` supports `auto | none | required`, specific functions, and `AllowedToolsParam` (schema puts `allowed_tools` **inside** `tool_choice`). [The normative explanation](https://www.openresponses.org/specification#tool_choice) says `required` must result in at least one tool invocation; [allowed-tools rules](https://www.openresponses.org/specification#allowed_tools) are hard constraints, not mere provider hints. `previous_response_id` requires prior structured input and output to be treated as preceding the new input, preserving order; `truncation: disabled` forbids silent truncation ([spec](https://www.openresponses.org/specification#truncation)).

## Streaming and transport

- [The 2026-04-24 SSE event union](https://www.openresponses.org/openapi/2026-04-24/openapi.json) lists 24 variants: `response.created`, `.queued`, `.in_progress`, `.completed`, `.failed`, `.incomplete`; `response.output_item.added/done`, `response.content_part.added/done`, `response.output_text.delta/done` and `response.output_text.annotation.added`, `response.refusal.delta/done`, `response.reasoning.delta/done`, `response.reasoning_summary_part.added/done`, `response.reasoning_summary_text.delta/done`, `response.function_call_arguments.delta/done`, and `error`. All schema variants require `type` and `sequence_number`; terminal response events carry a full `ResponseResource` snapshot. A streaming error is followed by `response.failed` ([spec, Errors](https://www.openresponses.org/specification#errors)). Neither `finishReason` nor a single text delta represents the full event model.
- An output item's first own event is `response.output_item.added`; streamable text content then uses `response.content_part.added`, matching text delta/done events, `response.content_part.done`, and finally `response.output_item.done` ([spec, Items](https://www.openresponses.org/specification#items)). This does not preclude earlier response-level `response.created/queued/in_progress` events. SSE requires `Content-Type: text/event-stream`, a matching SSE `event` name and JSON `type`, and final literal `[DONE]` ([spec, HTTP Responses](https://www.openresponses.org/specification#http-responses)).
- Optional [WebSocket transport](https://www.openresponses.org/specification#websocket-transport) uses the **same response and event model** at `/v1/responses`; client turns send `type: "response.create"` plus ordinary request fields, but omit HTTP-only `stream`, `stream_options`, `background`. The server must process at most one in-flight turn per socket. Continuation with `previous_response_id`, including `store: false` connection-local state and `previous_response_not_found`, has explicit rules ([spec, continuation](https://www.openresponses.org/specification#websocket-continuation)). The spec's WebSocket error envelope differs from ordinary SSE `error` ([spec, WebSocket Errors](https://www.openresponses.org/specification#websocket-errors)).

## Extensions and schema gaps

- Implementors MAY add `Item` types, but non-standard `type` values **MUST** use an implementor slug prefix such as `acme:search_result`. Extended items and their trajectories SHOULD be treated as nonportable; every trajectory item is said to require `id`, `type`, and `status` ([spec, Extending Items](https://www.openresponses.org/specification#extending-items)). Hosted tool extensions should have matching receipt item types that can be round-tripped on follow-up ([spec, Extending tools](https://www.openresponses.org/specification#extending-tools)).
- New streaming event types MUST likewise be slug-prefixed and have `type` and monotonically increasing `sequence_number`. They MUST NOT alter core stream semantics and clients MUST be able to ignore unknown extension events without losing the ability to reconstruct the canonical response ([spec, Extending streaming events](https://www.openresponses.org/specification#extending-streaming-events)). Implementor-specific optional fields on existing schemas MAY be added, but MUST NOT change required core behavior and reduce portability ([spec, Extending existing schemas](https://www.openresponses.org/specification#extending-existing-schemas)).
- **Normative prose/schema mismatch to handle explicitly:** [ItemParam](https://www.openresponses.org/openapi/2026-04-24/openapi.json), [ItemField](https://www.openresponses.org/openapi/2026-04-24/openapi.json), [ResponsesToolParam](https://www.openresponses.org/openapi/2026-04-24/openapi.json), and the SSE `oneOf` list enumerate only known standard alternatives; many _input_ item param schemas have optional/nullable `id` and optional/absent `status` despite the prose requiring those fields on every trajectory item. Strict generated standard unions therefore do **not** describe all legal extensions. Preserve opaque, validated prefixed extensions separately if required, and distinguish incoming request item params from materialized output/trajectory items.
- The prose calls `allowed_tools` a field while the dated schema represents it as `tool_choice: { type: "allowed_tools", tools: [...] }` ([spec](https://www.openresponses.org/specification#allowed_tools), [OpenAPI](https://www.openresponses.org/openapi/2026-04-24/openapi.json)); the prose says request bodies MUST be JSON, whereas the [reference](https://www.openresponses.org/reference#request-parameters) and schema also list form encoding. Resolve implementation decisions against the chosen dated release and do not silently claim wider compatibility on these disputed edges.

## Router implications (recommendations, not spec text)

Pin `2026-04-24` at the type boundary; keep transport and route selection outside the OpenResponses request and event objects. Treat unsupported standard fields and nonportable extensions as explicit capability checks, not silently dropped values. Test round trips of multi-item outputs, multimodal input and tool output, streamed item/content ordering, `response.incomplete/failed`, absent usage, and prefixed opaque extensions against the [official compliance tests](https://www.openresponses.org/compliance) where applicable.
